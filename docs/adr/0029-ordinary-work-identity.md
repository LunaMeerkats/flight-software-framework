# ADR-0029: Runtime-issued identity during ordinary work

- Status: Accepted for this bounded API increment
- Date: 2026-10-23
- Scope: Selected application identity in the existing ordinary-work context

## Context

ADR-0028 defers service expansion until a concrete consumer needs callback-time
acceptance feedback. Root Codex and independent consumer_need assess a diagnostic
producer that commits an effect only after its event is accepted. Existing public
APIs can express this: an application can borrow a caller-owned queue and clock,
or a mission can share them through checked interior mutability. The remaining
gap is source attribution. Ordinary work cannot obtain its own runtime-issued
identity, so registration must wire that identity back into retained application
state, often through a separate optional cell. This creates avoidable missing or
mispaired identity state. Message callbacks already receive their selected ID.

RFF-LIB-REQ-004 revision 1 is established before implementation. Input is clean
codex/nightly at a9afb328905eb2d413a868bc7e0371a06b5c6c20; the full locked local
baseline passes 168 tests. This is source assessment, not an external user study.

## Decision

Add a read-only `application_id()` accessor to `ApplicationWorkContext`. Its
private constructor receives the ID selected by `Runtime::work`; all existing
owners and wrappers continue to delegate through that one path. The callback
signature, associated errors and immutable configuration view remain intact.
Rejected lifecycle requests never invoke application code. In-place restart
retains the record's ID. No identifier is generated by the context.

Verify a public-only diagnostic producer which uses this ID for `EventSource`,
borrows a mission-owned RefCell queue with `try_borrow_mut`, observes immediate
acceptance, and commits a bounded observation only after Recorded. Full or busy
queue errors are explicit mission-selected terminal work errors. Failure-event
wrappers receive a separate queue so they do not hold the diagnostic queue's
mutable borrow across the callback. The host drains between calls. A
mission-owned Cell-backed clock permits controlled readings without permanently
borrowing a mutable ManualClock. These are consumer policies, not new services.

## Alternatives considered

- Host-mediated event staging cannot make callback success depend on actual queue
  acceptance. It remains suitable when that ordering is unnecessary.
- Post-registration `Cell<Option<ApplicationId>>` wiring works today, but adds
  missing-ID handling and can attach the wrong runtime or peer ID. Supply the
  selected value through the existing context instead.
- A new event-bearing work trait/context or a shared framework queue abstraction
  could remove mission borrowing code, but also needs event-ID typing, queue
  ownership, clock and saturation policy across every work owner. Defer it until
  this narrower API and checked mission composition prove insufficient.
- A permanent `&mut EventQueue` in the application prevents host drain or sharing
  that queue with failure reporting while the runtime owns the application.
  Checked mission interior mutability permits serial access with an explicit busy
  error; it does not provide synchronization or concurrency support.

## Evidence and consequences

The existing `ApplicationId` contract governs scope and equality. Official Rust
Cell and RefCell documentation informs only the consumer's interior-mutability
policy, recorded in SRC-RUST-WORK-IDENTITY. No upstream implementation is copied.
The [focused review](../verification/WORK_IDENTITY_REVIEW.md) will record actual
tests, source identity, independent review and exact hosted evidence.

The API adds one copied runtime-local value to a privately constructed context.
It does not bind events to a runtime, authenticate sources, validate clock origin,
grant lifecycle access, or provide event/messaging services. Cross-runtime IDs
can compare equal. Applications remain able to fabricate EventSource values.
Queue acceptance is not transactional with a later external effect; a later
failure does not retract a recorded event. No atomicity or reliable I/O is claimed.

## Risks and revisit conditions

RefCell borrow conflicts require mission policy and remain possible even in
serial code. Full-event errors are terminal under the existing cooperative work
contract; panics, hangs and allocator exhaustion remain uncontained. The frozen
consumer tests do not prove external adoption, API stability or qualification.
Revisit narrow event capability injection when a concrete consumer needs to
remove this borrowing policy or compose services beyond it. Existing separate
consequential gates remain unchanged.
